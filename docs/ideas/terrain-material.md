# Terrain material: geology, detail, grass, wetness and snow in one

The landscape bench (docs/bench/landscape) found that the ground cannot show everything the engine knows about it
at once. The generator gives geology (soil, bare rock, scree, alluvium; `get_geology_shader_code()`) and erosion
detail below the vertex spacing (`get_detail_shader_code()`), GrassField3D gives the thatch under the grass
(`get_ground_shader_code()`), and the weather and the snowpack give wetness and snow. Wetness and snow exist only
as `BaseMaterial3D` features (`wetness_enabled`, `snow_enabled`), generated into its shader and, under path
tracing, applied in the ray generation shader from material flags (`subsurface.wetness`, `subsurface.snow`). The
geology and detail code only fits a `ShaderMaterial`. So the bench draws the ground as a `StandardMaterial3D`
with vertex colours: snow and wetness work, the geology look is a flat tint and the detail normals are gone.
Every terrain in a real scene hits the same wall, Terrain3D's own shader included.

## How others do it

- **Frostbite, Andersson 2007, "Terrain Rendering in Frostbite Using Procedural Shader Splatting"** (SIGGRAPH
  course): the terrain shader is assembled from rules on height, slope and normal, evaluated per pixel; artists
  paint masks only where the rules are not enough. Layers blend in the shader, not in a baked texture.
- **Far Cry 5, Moore 2018, "Terrain Rendering in Far Cry 5"** (GDC): world-space procedural layer weights from
  height, slope and flow maps, with a virtual texture cache; cliffs use a separate world-aligned (triplanar)
  path so steep faces do not stretch.
- **The Witcher 3, Gollent 2014, "Landscape Creation and Rendering in REDengine 3"** (GDC): two layers per
  texel (background and overlay) chosen by slope, with a slope-based blend and vertical-face projection.
- **Height-based blending, Mishkinis 2013, "Advanced Terrain Texture Splatting"**: each layer's height map
  decides who wins near a transition (stones poke through sand), instead of a soft cross-fade that looks like
  paint.
- **Biplanar mapping, Quilez 2020**: two texture fetches instead of triplanar's three, picking the two major
  axes; enough for cliffs and much cheaper, which matters under path tracing where every hit shades.
- **Unreal Engine 5**: Landscape Layer Blend node (weight or height blend) plus material functions for snow and
  wetness that projects share; Runtime Virtual Texturing caches the blended result. Snow and wetness are not
  built in; they are material functions driven by Material Parameter Collections.
- **Unity HDRP**: TerrainLit shader with four to eight layers, height-based blend; snow and wetness are again
  project-side Shader Graph sub-graphs reading global properties.
- **Wet surfaces, Lagarde 2013** (already used by `wetness_enabled`, see material-wetness.md) and **snow cover,
  Niu and Yang 2007** with the per-facet rule (already used by `snow_enabled`, see snow.md): these are the lines
  to reuse, not rewrite.

The common shape: one terrain shader built from reusable functions (layers by rules, height blend, world-aligned
cliffs, then weather on top), the weather functions shared with every other material.

## What we build

1. **The weather lines as shader code any material can use.** `BaseMaterial3D.get_wetness_shader_code()` and
   `get_snow_shader_code()` return the global uniforms and two functions,
   `weather_wetness(world_pos, world_normal, porosity, metallic, inout albedo, inout roughness)` and
   `weather_snow(world_pos, geo_normal, detail_normal, amount, max_slope, inout albedo, inout roughness, inout normal)`,
   generated by the same C++ that writes them into `BaseMaterial3D`, so there is one source and the two never
   drift apart. Under path tracing a `ShaderMaterial` already runs its own fragment code in a custom hit group,
   so the same lines run there with no ray generation flags; the check below confirms the global maps are bound
   for custom hit shaders. This alone fixes Terrain3D (its shader override takes the snippets).
2. **`TerrainMaterial3D`**, a material that writes its own shader like `BaseMaterial3D` does, so nothing is
   pasted by hand:
   - layers (albedo, normal, roughness, height) for rock, scree, soil, alluvium, sand, plus an optional grass
     layer; weights from the generator's geology globals (`terrain_geology`) and the data map (slope, wetness
     index), with Mishkinis height blending;
   - biplanar mapping above a slope threshold, plain world XZ below it;
   - the generator's detail normal (`terrain_detail_normal`, footprint-faded);
   - GrassField3D's ground tint where grass grows;
   - then wetness and snow from step 1, in that order (snow over wet ground, as the snowpack does).
   Without a generator it falls back to slope and height rules, so it also serves hand-made terrain.
3. The landscape bench switches its ground to it and the GAP line becomes a check.

## Far ground: plant cover colour past far_start (11 Nov)

Distant terrain reads by its cover, not its soil: a forested slope at 2 km is dark green even where no plant is drawn.
Engines bake a world colour map for the far field (Frostbite's terrain colour map, Andersson 2007; Far Cry 5's world
colour map, McLaren 2018; UE's landscape macro variation). Here the ground colour itself already comes right at
distance (geology map plus each layer texture's lowest mip), so only the cover is new. Vegetation publishes
`terrain_cover_map` (RGBA8: sRGB mean cover colour from above with canopy shade, alpha the cover share) and
`terrain_cover_rect` (x, z, width, depth), 4 m texels, from the same colours `vegetation_far()` uses.
`far_blend_enabled` (off by default; the code is only compiled when on) blends, between `far_start` (300 m) and
`far_start + far_fade` (150 m), from the near result (grass tint, `vegetation_far()`) to the bare ground under the
cover colour by its share, so the far cover replaces `vegetation_far()` and nothing stacks. It sits after the layer
blend and detail normal and before ground deformation, wetness and snow, which still lie on it. Unset globals (rect
width 0) leave the ground as it is. Distance is from the camera to the shaded point, the same rule
`vegetation_far()` uses, also on path-traced bounce hits.

## Sky occlusion: raster ambient light only from the sky the hills leave open (12 Nov)

The fault: at dusk a slope under a higher ridge was lit red in raster and dark under path tracing. With the sun
switched off the raster frame barely changed (6.4 against 6.6), so the light was the sky's: raster ambient light
integrates the whole sky around the normal (the radiance map), including the low sunset glow that the far valley
wall hides. The path tracer traces the wall and the slope goes dark (2.6). Daytime valleys carry the same error,
weaker. Screen-space AO reaches a few metres; this is hundreds.

How others do it:

- Horizon mapping (Max 1988) and the sky view factor of a sloped surface under its terrain horizons (Dozier and
  Frew 1990), the standard in terrain radiation models; our climate bake already uses both (`terrain_climate.h`).
- Bent normals and a scalar occlusion (Landis 2002; Unreal's distance field AO for the sky light; Godot's
  `BENT_NORMAL_MAP`). Open worlds bake a top-down world AO from the heightfield.
- Precomputed visibility as spherical harmonics (Sloan, Kautz and Snyder 2002), with order 2 enough for irradiance
  (Ramamoorthi and Hanrahan 2001).

What we tried, measured at three ground points against the exact integral of the real sunset panorama:

| method | left slope | right slope | floor |
|---|---|---|---|
| exact (the panorama, the horizons, the cosine) | 0.59 | 0.66 | 0.82 |
| sky view factor + bent normal (v1) | 0.91 | 0.76 | 0.84 |
| first-order harmonics on the pixel normal | 0.61 | 0.60 | 0.68 |
| second-order harmonics (built) | 0.58 | 0.67 | 0.80 |

A ratio per 8 m cell weighted by the sky's light (v2) rendered barely darker: the cell's normal is not the pixel's.
A view factor treats the sky as even; at dusk nearly all of it is a band a few degrees high in the west, exactly
what a ridge hides, so the occlusion must be weighed by the sky's own light, and per pixel normal (the 8 m cell's
normal can face the other way from a gully side).

What we build:

- `TerrainGenerator3D.sky_occlusion` (default on), after `generate()`: the final ground on a grid `sky_cell` (8 m)
  apart, horizons in 16 directions out to `sky_distance` (4 km, steps growing 8%, past the result the ground counts
  as level), kept per node (16 bytes). About 0.8 s for the 4 km valley.
- The sky's light: `sky_light_source` (a WorldEnvironment or Camera3D) is read back as a 64x32 radiance panorama
  (`RenderingServer.sky_bake_panorama`) every `sky_light_interval` (2 s), and only when it has changed by more
  than 2%. It is gathered into 16 x 16 direction bins; each node's seen sky (bins above its horizons, the horizon's
  bin in part) goes into nine harmonics of luminance, over the whole sky's first. About 90 ms on worker threads for
  513 x 513 nodes; `update_sky_light(panorama)` does the same by hand. Before any panorama, an even sky.
- Three layers of RGBA half (`terrain_sky_map`, a sampler2DArray) and the whole sky's harmonics
  (`terrain_sky_full`, `terrain_sky_full2`, `terrain_sky_full3`) as globals.
- `TerrainMaterial3D.sky_occlusion_enabled` (default on), raster only (`#if !defined(RT)`): `AO` = irradiance of the
  seen sky over that of the whole sky, both on the shading normal (so the detail normal keeps its shading),
  `AO_LIGHT_AFFECT` 0 (direct light untouched), then the multi-bounce fit of Jimenez et al. 2016 (GTAO) on the
  ground's albedo, since the hidden sky is replaced by lit ground, not black. `sky_occlusion` scales it.
  Small-scale occlusion stays with SSAO.

Result (valley view, mean pixel value, raster without / with / path traced): dusk ground 1.42 / 1.00 / 1.07, the
slope under the west wall 2.60 / 1.82 / 1.06; afternoon ground 24.4 / 22.2 / 22.8, a shaded slope 16.4 / 11.9 /
13.6 (raster has no bounce light from the sunlit wall opposite).

Cost: three bilinear fetches and two nine-term sums per ground pixel; the readback is a 64x32 copy every few
seconds while the sky changes. GPU timings on the PC before merge are owed.

## Cost and quality

- Raster: biplanar doubles fetches only on steep pixels; five layers with height blend is about what Terrain3D
  already pays. Expect a small cost against the vertex-colour stand-in and a large gain (real surfaces, detail
  normals under 4 m). Measured on the PC before merge.
- Path tracing: the custom hit group shades every terrain hit with the full layer stack; bounces see the same
  ground, so the detail is not lost under path tracing (the project rule). The cost is one heavier hit shader;
  measure with `--gpu-profile` on the PC.
- No visual loss for existing scenes: nothing changes unless a material uses the new code.

## Check

- Bench: raster and path traced 100% crops of a snowy rock face, a wet riverbank and a beach, before (stand-in)
  and after; snow and wetness must match `StandardMaterial3D` on a flat test patch within a few percent.
- Confirm `snow_map`, `snow_world_map` and `weather_state_map` are readable from a custom hit shader under path
  tracing; if not, bind them the way the ray generation shader does.
- GPU timings on the PC (raster frame time, path traced hit cost).
